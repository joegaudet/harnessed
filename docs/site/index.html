Test harnesses for components and pages

Write the harness once. Run it under every runner*.

Like page objects, but for components too. One harness API for Testing Library, node:test, Bun, Playwright, Cypress, WebdriverIO, Nightwatch, Vitest browser mode, Puppeteer, TestCafe, Ember and Angular, over React, Vue, Solid and Svelte alike, with Gherkin on top and Storybook play functions beside. The same class drives a fast jsdom unit test, a story, and a real-browser end-to-end test.

Get started GitHub
$ npm i -D @harnessed-ts/core @harnessed-ts/dom

Then add the driver package for your runner.

* Well, every one with a solid border below. The dashed ones haven't been through the conformance suite yet. Bring snacks.

Why harnessed

One API across the whole test pyramid

Write once

The same harness class drives jsdom unit tests and real-browser end-to-end tests.

Every runner

Testing Library, node:test, Bun, Playwright, Cypress, WebdriverIO, Nightwatch, Vitest, Puppeteer, TestCafe, Ember and Angular, plus Storybook play functions.

Strict by default

Ambiguous matches fail loudly, and absence answers immediately, under every driver.

Framework-agnostic

Harnesses query the DOM, not React, Ember, Vue, Solid, Svelte or Angular.

Concepts

What a harness is

A class that drives a component the way a person would, through methods named for what the component does. Tests state intent; the harness owns the DOM wiring. 

@Harness({ host: testId('login-form') })
class LoginFormHarness extends ComponentHarness {
  @ByLabel('Email') private accessor email!: Query
  @ByLabel('Password') private accessor password!: Query
  @ByRole('button', { name: /sign in/i }) private accessor submit!: Query
  @ByTestId('login-error') private accessor errorLine!: Query

  async signInAs(email: string, password: string): Promise<void> {
    await this.email.fill(email)
    await this.password.fill(password)
    await this.submit.click()
  }

  async error(): Promise<string | null> {
    if (await this.errorLine.isAbsent()) return null
    return this.errorLine.text()
  }
}
jsdom, via Testing Library
render(<LoginForm />)
const form = new LoginFormHarness(dom({ user: userEvent.setup() }))
await form.signInAs('ada@example.com', 'hunter2')
expect(await form.error()).toBeNull()
A real browser, via Playwright
const form = new LoginFormHarness(pw(page))
await form.signInAs('ada@example.com', 'hunter2')
await expect(form).toBeAbsent()

Mocking

Mock the API once, under every runner

@harnessed-ts/mock describes the backend a test needs, and each driver intercepts requests its own way — page.route under Playwright, cy.intercept under Cypress, fetch and XHR patched in the page under Testing Library, Ember and Storybook. The same handlers, held to the same conformance catalog, under every runner. 

@Api({ base: '/api/users' })
class UsersApi extends ApiHarness {
  @Get('/:id')
  byId({ params }: MockRequest<{ id: string }>) {
    return params.id === '1' ? json({ name: 'Ada' }) : notFound()
  }
}
jsdom, via Testing Library
const api = mock(dom({ user }), { scope: '/api/**' })
await api.use(UsersApi)
render(<Profile id="1" />)
expect(await profile.name()).toBe('Ada')
A real browser, via Playwright
const api = mock(pw(page), { scope: '/api/**' })
await api.use(UsersApi, { byId: () => serverError() })
await profile.goto()
expect(await profile.error()).toBe('500')
  • Builders for every format: JSON, text, files, forms, problem details, JSON:API, GraphQL, server-sent events and NDJSON streams, network errors and hangs.
  • Nothing goes unanswered by accident: a request no mock answers fails the test, naming it. Requests are logged with parsed bodies, and every assertion style can check them.
  • Mocks that cannot drift: validate them against an OpenAPI document or a GraphQL schema, type them from openapi-typescript, replay a HAR, or reuse MSW handlers.
  • WebSockets, state and test data: mocked sockets, per-test state, and deterministic factories.

Patterns

Use cases

One harness from unit test to end-to-end

Write selectors once. The harness that drives a component in a jsdom unit test drives the same component in a real browser, so the end-to-end suite never grows a second set of selectors that drifts out of step with the first.

Behaviour is held to the same rules under every driver: absence answers immediately, single-target operations are strict, and scopes don't leak. See the guarantees.

Page objects

@harnessed-ts/page gives one test object per screen: what it's made of, how to know it has arrived, and how to get there by URL. Pages construct under every driver; only goto() needs one with an address bar. 

@Harness({ host: testId('page-checkout') })
class CheckoutPage extends PageHarness<{ token: string }> {
  override get path() {
    return '/checkout?token=$token'
  }

  @ChildHarness(CartHarness) accessor cart!: CartHarness

  protected async waitForReady(): Promise<void> {
    await this.self.waitFor('visible')
  }

  async placeOrder(): Promise<ConfirmationPage> {
    await this.cart.checkout()
    return this.transitionTo(ConfirmationPage)
  }
}

Stories that test themselves

@harnessed-ts/storybook hands every play function its harness. Each harness method shows up as one step in the Interactions panel, with its clicks and keystrokes nested underneath, and Storybook's Vitest addon runs the same plays as tests. React and Ember stories alike.

The stories double as end-to-end fixtures: StoryPage opens one by URL from Playwright or any runner that navigates, before or after its play function runs. 

import * as LoginStories from './LoginForm.stories'

const story = await StoryPage.goto(pw(page), LoginStories, 'WrongPassword', { play: false })
await story.harness(LoginFormHarness).signInAs('ada@example.com', 'hunter2')

BDD with Gherkin

@harnessed-ts/gherkin adds a page registry, a {page} parameter type and a world for playwright-bdd, cucumber-js, Cypress cucumber, ember-cli-yadda and Nightwatch. Steps call harness methods, not selectors. 

Feature: Checkout
  Scenario: Paying for the cart
    When I open the checkout page
    Then the total is "$90.00"
When('I open the {page} page', async ({ page, world }, name) => {
  world.checkout = pages.open(name, pw(page))
  await world.checkout.goto()
})

Then('the total is {string}', async ({ world }, total) => {
  expect(await world.checkout!.total()).toBe(total)
})

Tooling

  • @harnessed-ts/mock: one way to mock the API under every runner — handlers, API harnesses, response builders, factories, and checks of what was requested.
  • @harnessed-ts/eslint-plugin: keeps selectors and runner-specific mocks out of tests, and keeps harnesses speaking in behaviours rather than runner or DOM vocabulary.
  • @harnessed-ts/chai and @harnessed-ts/qunit: absent, selected and readAs assertions, and checks of mocked requests, for runners that don't use expect.extend.
  • @harnessed-ts/config: one harnessed.config.ts for shared settings such as the test-id attribute.
  • @harnessed-ts/claude: installs a Claude Code skill that writes harnesses in your project's conventions.
